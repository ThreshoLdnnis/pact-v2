# 答辩讲稿与演示顺序

建议总时长6分钟，可根据赛事要求调整。PPT为可编辑文件，现场演示使用新合成数据库，避免上一轮余额和订阅状态干扰。

## 0:00-0:40 项目定位

PACT把自然语言金融请求拆成可检查的任务计划。核心问题是：模型理解请求之后，谁有权执行、怎样约束未来资金、怎样证明交易真的完成。首版选择智能转账、账单分析、订阅管理，全部采用合成数据。

## 0:40-2:20 跨场景演示

输入“分析本月账单，取消视频会员，再给张三转账500元，至少保留1000元”。展示DAG的三个步骤。账单从银行流水计算，取消订阅和付款分别等待确认。确认后查看视频会员下一次资金承诺释放，再查看交易回执和余额变化。强调模型没有产生任何成功回执。

## 2:20-3:10 权限边界

新请求“给张三转账1001元”。展示红级来自Policy，申请并手动输入模拟验证码。明确这是模拟强验证，不是真实MFA。展示已保存回执中的transaction_id和verified=true。

## 3:10-4:10 约束与重规划

用大额请求触发“最低留存+未来承诺”约束拒绝，说明强验证也不意味着可以透支未来承诺。改为小额重规划，观察版本变化和已有成功步骤复用。暂停/恢复不会撤销已入账交易。

## 4:10-5:10 后端可信执行

解释同一写事务覆盖审批重查、日累计、双边账务、幂等、审批消费和回执。展示8并发重试只执行一次的测试，说明返回模型文字不算交易成功。展示对账与审计入口。

## 5:10-6:00 验证与限制

报告当前自动化测试、真实HTTP验收和依赖扫描证据。默认是规则演示规划，Ollama候选适配已实现但真实推理未连测。私有仓库主干保护受套餐限制，PR流程是团队约定；不将演示PIN、模拟验证或本地哈希链包装为生产级安全能力。

## 常见问答

- 为什么不优先做复杂UI？工作台只承担请求、DAG、审批和回执解释，验证重点在权限和账务执行边界。
- 为什么加入Commitment Graph？相同余额背后存在未来房租和订阅，单查余额无法判断当前可执行金额；本版只保留账户与资金承诺边。
- 如何防模型幻觉？模型只能输出闭合候选Schema，服务端读取事实并判权，Banking生成回执，Agent查询核验之后才完成步骤。
- 如何防止点击两次扣两次？服务端固定步骤幂等身份，并以数据库唯一约束和串行写事务兜底，测试覆盖8并发重复请求。
- 为什么定时转账到期还要授权？到期当天的累计和资金承诺可能变化。登记只返回scheduled，到期生成新任务并重查规则，不把登记当付款。
- 是否已经支持真实银行？没有，所有数据合成，工具白名单没有真实银行网络调用。

现场备选：打开reports/http-smoke.json和回执截图说明实际验证证据。不得把预录截图说成现场执行。
